# Расшифровка встреч

## Что есть

- Сервис calls-recognize: контейнер Docker «calls-recognize», http://localhost:7861. Папку проекта (где лежит docker-compose.yml) дальше называем <проект>.
- Записи кладутся в <проект>/input/ (в контейнере /app/input).
- Результат: <проект>/output/<имя файла>/ (если папка занята прошлой расшифровкой — «<имя> (2)» и т.д.):
  - <имя>.txt — текст; с разметкой говорящих строки вида «Говорящий 1: …»;
  - <имя>.srt — те же реплики с таймкодами от начала записи, говорящий в квадратных скобках;
  - meta.json — модель, длительность, partial, created, recorded, speakers, hallucinations_removed, lost_speech_repaired, lost_speech_left, diarization_error.
- Сервис сам:
  - подсказывает модели термины из словаря (get_terms / set_terms, хранится в output/settings.json);
  - вырезает типовые выдуманные фразы и повторы;
  - перераспознаёт куски, где речь потеряна; что не удалось — пишет в lost_speech_left;
  - по запросу размечает говорящих «Говорящий N». Имён сервис не знает.

## Порядок работы

### 1. Проверить сервис

```bash
curl -s -o /dev/null -w "%{http_code}" http://localhost:7861/
```

Если ответа нет: спросить пользователя, можно ли поднять контейнер (`docker compose up -d` в <проект>). Без согласия не запускать.

### 2. Положить запись в input

- Если пользователь не дал файл, спросить, где лежат записи, и не искать по всему диску.
- Скопировать файл (не перемещать) в <проект>/input/.
- Если файл с таким именем там уже есть и это другая запись, переименовать копию.
- Перед запуском проверить <проект>/output/<имя>/ и список задач: если запись уже расшифрована, заново не запускать.
- Папки и файлы для API называть латиницей: путь с кириллицей веб-слой может отклонить с «404: Not Found».

Пользователю одной строкой назвать, какую запись взял: имя, длительность.

### 3. Запустить расшифровку

Вызов API в два шага: POST возвращает event_id, GET отдаёт ответ. Вспомогательная функция:

```bash
cr() { local id; id=$(curl -s -X POST "http://localhost:7861/gradio_api/call/$1" -H 'Content-Type: application/json' -d "{\"data\":$2}" | node -e 'let s="";process.stdin.on("data",d=>s+=d).on("end",()=>console.log(JSON.parse(s).event_id))'); curl -s -N --max-time 60 "http://localhost:7861/gradio_api/call/$1/$id" | sed -n 's/^data: //p' | tail -1; }
```

Запуск в фоне (ответ сразу, с job_id):

```bash
cr start_transcribe '["<имя файла в input>","large-v3-turbo",true,true,0]'
```

- Параметры по порядку: путь относительно input, модель, «каждая реплика с новой строки», разметить говорящих, число говорящих (0 — определить самому).
- Говорящих размечать всегда, когда нужен разбор «кто что сказал». Если число участников известно, передать его.
- Ход: `cr job_status '["<job_id>"]'` — status, progress, desc. Опрашивать не чаще раза в минуту.
- Остановить: `cr cancel_job '["<job_id>"]'` — распознанное сохранится как partial.
- Словарь терминов: `cr get_terms '[]'`; заменить целиком: `cr set_terms '[["Термин один","Термин два"]]'`. Это запись в настройки сервиса — только с согласия пользователя. Whisper принимает подсказку до ~220 токенов, это примерно 50–60 терминов: добавлять то, что искажается регулярно.
- Другие вызовы: runtime, list_jobs, list_transcripts, read_transcript, list_models.

### 4. Проверить расшифровку на ошибки

Сначала прочитать meta.json:

- lost_speech_left — куски, где речь потеряна и восстановить не удалось: назвать пользователю с таймкодами;
- lost_speech_repaired — восстановленные куски: проверить по смыслу, что текст не выдуман;
- hallucinations_removed — что вырезано: если вырезана реальная реплика, вернуть по смыслу;
- diarization_error — разметка говорящих не удалась, текст без меток;
- partial: true — расшифровка остановлена на середине: сказать, до какой минуты она дошла (covered, в секундах).

Затем прогнать скрипт для провалов, которые сервис не поймал (длинные паузы):

```bash
node <папка скилла>/srtcheck.js "<проект>/output/<имя>/<имя>.srt"
```

Скрипт выводит ПРОВАЛ, ПАУЗА, ГАЛЛЮЦ, ПОВТОР с таймкодами.

### 5. Исправить термины

Прочитать glossary.md рядом с этим файлом и исправлять по нему термины, имена и отчества. Заменять только там, где контекст это подтверждает. Неразобранное помечать «(не разобрано)», не угадывать.

Новые устойчивые ошибки, найденные при разборе, дописывать в glossary.md.

### 6. Говорящие

- «Говорящий N» сопоставлять с людьми по смыслу: кто представляется, к кому обращаются по имени. Сопоставление называть пользователю как вывод, не как факт.
- Участник, сказавший за всю запись меньше 5 секунд, отдельной метки не получает: его слова уходят соседнему говорящему.
- Разметка ошибается на перебиваниях и коротких репликах («Да», «Угу»): содержательные выводы о том, кто что сказал, делать по длинным репликам.
- Если число меток заметно расходится с числом участников, сообщить пользователю и предложить перезапуск с заданным числом говорящих.
- Если есть вторая расшифровка той же встречи (например, протокол из сервиса видеозвонков с именами), использовать её для сверки потерянных фрагментов, имён и терминов. Галлюцинации бывают в обеих.

### 7. Разбор встречи

По умолчанию ответ такой:

- одна строка: что за встреча, дата, длительность, кто участвовал;
- по каждой теме: суть вопроса, ответы по существу, договорённости;
- договорённости разделять по тому, за кем они;
- кто говорит, определять по разметке и смыслу, не выдумывать.

### Длинные записи (больше 2–3 часов)

Резать на части по часу внутри контейнера и ставить одной задачей на папку:

```bash
docker exec calls-recognize sh -c 'cd /app/input && mkdir -p <папка> && ffmpeg -v error -y -i "<запись>.mp4" -vn -ac 1 -ar 16000 -f segment -segment_time 3600 -reset_timestamps 1 "<папка>/<префикс>_%02d.wav"'
```

Затем склеить srt частей с абсолютным временем (смещение = номер части × 3600). Номера говорящих между частями не совпадают.
